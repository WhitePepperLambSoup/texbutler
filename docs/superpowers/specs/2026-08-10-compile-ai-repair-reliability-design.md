# 编译诊断与 AI 修复链可靠性设计

日期：2026-08-10
状态：已确认方案，待实施
目标分支：`codex/fix-compile-ai-repair`

## 1. 背景

用户在 TeXButler 内使用 XeLaTeX 编译时遇到以下连续故障：

1. 编译器返回失败状态，但日志解析器没有生成具体问题，界面只显示“退出码异常，未能从日志中解析出具体错误”。
2. 错误没有文件与行号，AI 上下文却把源文件第 1 行渲染为“第 0 行出错”，诱导模型猜测 BOM、编码、文档类或字体问题。
3. 一键修复生成的 unified diff 包含多个删除后原样添加的空修改 hunk；当前应用器把任意一个空 hunk 视为整份 diff 失败。
4. 普通 AI 对话中，模型把 `read_file`、`replace`、`insert_after` 等工具 JSON 放入代码围栏并在前面附加一句说明时，解析器不识别，工具调用被直接显示给用户而未执行。
5. 问题面板的“AI 解释/一键修复”把消息追加到当前活动文件的会话，而不是问题所属文件的会话，导致后续追问可能拿到另一个 TeX 文件的上下文。

这些问题共同造成错误信息缺失、AI 猜测、无效补丁循环以及跨文件上下文错乱。

## 2. 目标

- 编译失败时尽可能保留并解析 XeLaTeX/MiKTeX 的真实控制台输出。
- 绝不把未知行号伪装为第 0 行或把第 1 行错误标记为故障点。
- 一键修复只向 AI 提供真实、可追溯的错误信息；没有可操作输出时明确停止，不让模型盲猜。
- mixed diff 中的空 hunk 可安全跳过；只有整份 diff 都没有真实变化时才拒绝。
- 对明确的修改类用户请求，兼容模型输出的 fenced JSON 工具调用，同时继续执行现有路径、文件类型、快照与回滚保护。
- 问题解释和修复记录进入问题所属文件的持久化 AI 会话。

## 3. 非目标

- 不修改用户项目中的 `q2_en.tex`、`main.tex` 或其他 LaTeX 文件。
- 不根据通用错误自动添加 `ctex`、字体或编码选项。
- 不放宽 AI 可写文件范围；仍只允许项目内 `.tex`、`.bib`、`.sty`、`.cls`。
- 不允许任意 JSON 或普通代码示例触发文件写入。
- 不改变现有最多三轮的一键修复策略，也不增加静默写入。

## 4. 方案概览

采用方案 B：修复完整数据链，而不是只修改提示词。

```text
XeLaTeX 进程
  ├─ 新生成的 .log ────────┐
  ├─ stdout/stderr ────────┼─> 统一诊断输入 ─> Issue(file, line?, raw)
  └─ exit status ──────────┘                         │
                                                     ├─> 问题所属文件 AI 会话
                                                     └─> 一键修复 prompt
                                                           │
                                             diff / 安全工具调用
                                                           │
                                              校验、快照、应用、重编译
```

## 5. 详细设计

### 5.1 编译输出采集与旧产物隔离

修改 `src-tauri/src/core/compiler/texlive.rs`：

- 每次系统 TeX 编译开始前删除本次主文件对应的旧构建 `.log`，避免失败进程没有刷新日志时读取上次编译结果。
- 不依赖旧 PDF 判断本轮错误；编译成功仍要求当前进程成功退出且 PDF 存在。
- 始终保留本轮 stdout 与 stderr，并使用有损 UTF-8 解码，确保 MiKTeX/TeX Live 输出中的非 UTF-8 字节不会让诊断完全消失。
- 优先解析新生成的 `.log`；若没有解析出错误，再解析本轮控制台输出。
- 写入供界面查看的日志时，优先保存新 `.log`；若其不存在或没有内容，保存控制台输出。
- 若两个来源都无法解析出结构化错误，合成一个 `Issue`：
  - `file` 设置为当前主文件相对路径；
  - `line` 保持 `None`；
  - `raw` 包含引擎名、退出状态和有长度上限的控制台尾部；
  - 消息明确说明是否完全没有控制台输出，而不是只说“检查控制台”。

控制台尾部必须设置字符上限，既保留最接近退出点的信息，也避免把超长日志全部送入 AI。

### 5.2 未知行号上下文

修改 `src-tauri/src/core/mod.rs` 中的 `SourceContext::around` 与 `render`：

- `line = Some(n)` 时维持现有行为，聚焦真实的第 `n` 行。
- `line = None` 时提供文件开头的有限上下文，但不设置 `focus`，行号从 1 开始，且不输出 `<<<< 此处出错`。
- 空文件和未知行号都不得产生第 0 行。

这样 AI 可以看到文档概要，但不会被错误地引导到 `\documentclass`。

### 5.3 无可操作诊断时阻止盲修

修改一键修复入口或 `fix_loop` 的前置校验：

- 如果 Issue 只有合成通用消息，且 `raw` 中没有任何实际引擎输出，则不调用模型。
- 返回明确结果：“编译器异常退出且没有输出，无法安全生成修复；请检查引擎安装或重新运行编译”。
- 如果 `raw` 含控制台尾部，则正常进入 AI 修复，因为模型已有真实证据。

判断必须依赖结构化标记或明确字段语义，不能靠本地化中文字符串模糊匹配。优先在编译器合成 Issue 时设置稳定的 `raw` 前缀，再由修复入口识别。

### 5.4 unified diff 空 hunk 处理

修改 `src-tauri/src/core/ai/fix_loop.rs`：

- 单个 hunk 内的 `-X`/`+X` 相同对继续按上下文处理。
- 如果处理完某个 hunk 后文件内容未发生变化，将该 hunk 标记为 no-op 并跳过，而不是立即让整份 diff 失败。
- 至少一个 hunk 产生真实修改时，返回最终内容。
- 所有 hunk 都是 no-op 时，返回“diff 没有实际修改”的明确错误，不进入写文件或编译阶段。
- 任何真实上下文不匹配、越界或歧义仍拒绝整份 diff；不能因为支持跳过 no-op 而放宽补丁安全校验。

同时强化修复提示：禁止为了维持 diff 格式输出未改变的行对，要求只保留真实修改 hunk。

### 5.5 fenced JSON 工具调用兼容

修改 `src-tauri/src/core/ai/chat.rs`：

- 保留现有三种格式：带 `【工具调用】` 标记、回复开头的 bare JSON、unified diff。
- 新增对 Markdown `json` 代码围栏中 ToolCall 对象的识别，兼容模型在工具前输出“我先读取文件”等简短说明。
- 只有当前用户问题明确属于修改意图时，才允许无标记 fenced JSON 中的写工具被执行。修改意图覆盖中英文常见动作，例如“修、改、添加、删除、替换、移动、生成、写入”和 `fix/change/add/delete/replace/insert/move/write`。
- `read_file` 可进入现有最多两轮的读取续接流程；读取后模型必须继续给出修改或最终回答。
- fenced JSON 仍必须反序列化为已知 ToolCall，且继续通过以下保护：
  - 项目内规范化路径解析；
  - 文档扩展名 allowlist；
  - 受保护目录拒绝；
  - anchor/old 唯一性校验；
  - 写入前快照；
  - 修改后编译验证与回滚入口。
- 普通教程、示例 JSON 或解释类提问不得执行工具。
- 用户可见文本移除已执行的 fenced JSON，只保留实际说明与执行结果。

### 5.6 问题所属文件的 AI 会话

修改 `src/store/aiStore.ts` 和必要的纯辅助模块：

- `diagnoseIssue` 与 `fixIssue` 不再无条件调用当前活动会话上下文。
- Issue 含 `file` 时，先确保该项目/文件已有持久化会话，再把请求与结果写入该文件会话。
- 如果问题文件不是当前编辑器文件，问题面板操作应打开该文件并切换 AI 面板绑定；操作按钮不能因为 `stopPropagation` 而绕过文件切换。
- Issue 没有文件时，保留当前会话，但修复后的编译器合成 Issue 通常会带主文件路径。
- 后续用户在该文件中追问时，历史只来自该文件会话，不会混入另一个 TeX 文件的内容。

异步返回仍使用现有 request context 快照，避免用户切换文件后旧结果覆盖新会话。

## 6. 错误与安全处理

- 删除的旧日志只限当前项目构建目录中的当前主文件 `.log`，不触碰用户源码。
- 控制台输出写入日志和 AI raw 前进行长度限制；API Key 等敏感信息仍通过现有脱敏路径处理。
- fenced JSON 不改变工具权限，只改善格式兼容。
- 工具调用解析失败时应给模型一次格式纠正机会或向用户显示明确失败原因，不能原样伪装成已执行。
- diff no-op 跳过仅适用于内容完全相同的变化；任何不确定匹配继续失败关闭。

## 7. 测试设计

所有行为先写失败测试，再写生产代码。

### Rust 单元与集成测试

1. `SourceContext::around(None)`：
   - 不产生 focus；
   - 渲染从第 1 行开始；
   - 不包含“第 0 行”或错误标记。
2. 编译诊断辅助函数：
   - `.log` 无问题但控制台含 `file:line` 错误时可解析；
   - 两者都不可解析时 Issue 带主文件、退出状态和控制台尾部；
   - 控制台完全为空时产生稳定的“不可安全修复”标记。
3. unified diff：
   - 一个真实 hunk 加多个 no-op hunk能够应用；
   - 全部 no-op 返回错误；
   - no-op 与上下文不匹配混合时仍拒绝。
4. fenced ToolCall：
   - “说明文字 + ```json + read_file”进入读取续接；
   - 修改意图下 fenced `replace/insert_after` 可执行；
   - 解释类问题中的示例 JSON 不执行；
   - 未知工具、外部路径、受保护文件仍拒绝。

### 前端与端到端测试

1. 从问题面板点击属于 `q2_en.tex` 的 AI 解释/修复时，自动切换并写入 `q2_en.tex` 会话。
2. 切回 `main.tex` 时看不到 `q2_en.tex` 的错误与修复历史。
3. 模拟无行号编译错误，界面显示 `q2_en.tex:?`，不显示 `?:?` 或第 0 行。
4. 模拟 fenced 工具调用，确认工具 JSON 不直接显示，文件按保护流程修改并可回滚。

## 8. 成功标准

- 附件中的通用 XeLaTeX 错误不再导致第 0 行和 BOM/字体无依据猜测。
- 有控制台错误时，问题列表与 AI 能看到真实输出；无任何输出时，一键修复明确停止。
- 附件形式的 mixed no-op diff 不再因为空 hunk 本身失败。
- “我先读取文件”后跟 fenced `read_file` 能被程序识别并继续执行。
- 问题修复对话始终留在错误所属 TeX 文件的持久化会话中。
- 所有新增回归测试、现有 Rust 测试、TypeScript 和生产构建通过。
